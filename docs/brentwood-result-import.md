# Brentwood historical result import

The import keeps source comparison, athlete identity and ownership separate. New public source profiles are unclaimed and identity-unverified. Existing profiles require an exact name or stored alias plus a specific corroborating historical club and compatible supplied gender. Claimed/private profiles, ambiguous names, inconsistent timings and conflicting same-edition records stay held. Club evidence does not create current club membership.

`brentwood-profile-import.py` snapshots the name/alias directory and scoped evidence with checkpoints. `lib/brentwood-source-plan.py` maps original HTML/spreadsheet headings, fixed-width heading/ruler columns, named JSON keys and headed PDF columns. Headerless 2011, 2012 and 2014 sheets remain research-only. Independent re-extraction found five additional 2008 gun-only finishers. Differences between the 2010/2013 source versions remain evidence; disputed places are omitted and name/time conflicts are held.

`apply-brentwood-profiles.py` requires the exact plan hash from a successful rehearsal before production publication. It rechecks name/alias and account state, screens newly added identities, checks each inserted source history, preserves original profiles and audits additions. Stable source identities make replay idempotent. Existing-history guards preserve privacy decisions and refuse an already recorded edition.

All plans, captures, credentials, database snapshots and receipts live outside this repository. The importer stores source evidence in the staff archive; public profile projections continue to omit provider URLs and review notes. Private correction jobs preserve original results and references before changing any fields. No historical Brentwood canonical-result seed exists to update.

Validation: `python scripts/verify-brentwood-profiles.py`, `node --experimental-strip-types scripts/verify-brentwood-plan.mjs <private-plan.json>` and `npm run verify:sources`. Rehearse on a disposable Neon branch, inspect all holds and receipts, then use the explicit production branch and `--publish`. The source registry additions remain manual-only.

## Resolving retained observations

`resolve-brentwood-held.py` rechecks the retained hold ledger against a fresh directory snapshot. Archived organiser tables now establish the 2011 headings, and individually corroborated club rows can resolve selected 2012 observations. The 2012 and 2014 spreadsheets still do not establish their own headings. Source versions, age/gender contradictions, privacy choices and same-edition collisions remain explicit checks.

`expand-brentwood-resolution.py` uses the headed 2010 companions and can create one provisional profile from a clear source-located appearance when no existing or near-name candidate exists. Other same-name appearances are not automatically attached. A matching specific historical club is still required for cross-edition consolidation. At most one new profile is proposed for each normalized full name.

`apply-brentwood-resolution.py` preserves previous histories, checks the actual content of stable source identities before replay, and compares the complete stored plan after publication. Existing targets additionally require unchanged birth date, gender, club references and historical matching evidence. The exact expanded plan must be rehearsed before production. Credentials, snapshots, held ledgers and receipts remain private. Run `python scripts/verify-brentwood-resolution.py` as well as the original regressions and application-schema checks.

If the directory changes after rehearsal, `refresh-brentwood-resolution-directory.py` refreshes the duplicate-screening names, aliases and accounts for the unchanged plan. It does not rematch existing targets or relax publication checks. New candidates cause explicit holds; an identity change during the refresh stops it again.

## Official 2026 table and further held-result resolution

`continue-brentwood-results.py` compares the FR Systems full 2026 table with all independently paginated provider rows, including source IDs, names, bibs, chip/gun times, club, gender, category and each placing. Edition metadata must establish the 22 March 2026 Half, 13.1 miles, complete unrestricted results and the expected version. Earlier club reports can bridge to this table only through a unique matching name or reviewed variant, exact time and, where necessary, the same specific club. Existing published results receive a separately reviewed before/after enrichment, never a duplicate result.

A headed 2013 organiser women's table corroborates retained rows. Matching 2010 organiser and timing-provider rows can recover export-truncated full names. Selected Serpentine and Northbrook records corroborate older observations. A club table's generic time stays a finish time of unknown chip/gun basis; club-list positions are not treated as overall race placings. Repeated bibs, source disagreements and unresolved identity candidates remain held.

Optional bounded first-name variants require all remaining name tokens to agree, explicit matching gender and a unique specific historical club match. This is separate evidence from an exact name or stored alias and is recorded as such. The default matcher remains exact-name/alias only. No account identity, alias, ownership or club membership is rewritten.

`refresh-brentwood-continuation.py` rescans the live name/alias directory for a fixed proposed batch immediately before rehearsal. New ambiguity or changed targets reduce the batch; refresh cannot expand it. `apply-brentwood-resolution.py --batch` supports isolated continuation batches, preserving existing history fingerprints, privacy checks, fresh-directory guards and complete stored-plan comparison. Apply additions first, then run `apply-brentwood-enrichments.py`; the latter locks and compares complete old/new histories and unchanged profile evidence in one transaction. Production requires the identical successful rehearsal plan hash. Replays create no further records.

Run `verify-brentwood-continuation.py` for eight synthetic variant/ambiguity/privacy/duplicate-edition regressions alongside the existing suites. Compare final stored performances and preservation of earlier histories, allowing only the explicit enrichment changes. Confirm no repeated public source keys or athlete/edition entries, inspect sample public pages for evidence leakage, and keep private plans, snapshots and source captures outside Git. Newly registered club archives remain manual-only.


## Individually corroborated club facts and reviewed consolidation

`deep-dive-brentwood-results.py` reconciles private, manually inspected club fact extracts with existing held keys. A unique edition/name/time match is required. A generic club finish time cannot supply chip/gun labels, bibs, category or placing from an unheaded sheet. Headed primary records retain their exact timing fields; conflicting dates, clubs and chip-time meanings stay held. The current pass reviewed 50 facts from 15 result reports: 34 held rows received individual corroboration and 14 headerless rows received supported field meanings. Separate identity checks authorize nine additions (three new profiles and six existing profiles); seven of the additions come from those 14 headerless rows.

`refresh-brentwood-continuation.py --batch` also supports later fixed proposals. It can only retain the originally proposed targets; a changed match becomes a hold. The latest refresh screened 945,170 profile names and aliases. Six additional synthetic source reconciliation cases exercise unheaded-field isolation, disagreement and ambiguity guards.

`merge-reviewed-brentwood-profiles.py` accepts a private, individually reviewed multi-edition manifest. It never decides identity from name similarity. It compares exact pre-merge profiles, histories, identifiers and the full athlete-reference schema, requires an identical isolated rehearsal, and refuses claimed profiles or unexpected references. It moves source histories without altering their performances, retains the retired row and original identifier, adds canonical aliases, makes the retired profile private, records a parent link and public redirects, and writes the before-state and evidence into a staff audit. Replay verifies the stored consolidation and makes no further changes. This keeps a separately evidenced duplicate resolution reversible and distinct from account ownership or verification.
